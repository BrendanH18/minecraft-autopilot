# Local bridge protocol v1

Discover the bridge through this project's `.runtime/bridge.json`, an installed game profile's `config/minecraft-agent/bridge.json` selected with `attach`, or a file selected with `--bridge`. Its `url` is an HTTP origin on `127.0.0.1`, `token` is a bearer token, `protocol` is 1, and `backend` is `fabric`, `mineflayer`, or `demo`. Treat the file as a credential. JSON requests are capped at 8192 bytes; authentication is required for every endpoint. The adjacent `.lock` file records a process ID and random ownership nonce; a second bridge cannot replace a live owner's discovery file.

Every request uses `Authorization: Bearer TOKEN`. POST requests also use `Content-Type: application/json`. Browser-origin requests are rejected. Responses are JSON; failed calls return `{ "error": "explanation" }` with a non-2xx HTTP status.

| Method | Endpoint | Request | Response |
| --- | --- | --- | --- |
| GET | `/v1/state` | None | State observation. |
| POST | `/v1/control` | `{ "action": "acquire", "leaseId": "UUID" }` | `{ "ok": true }` |
| POST | `/v1/control` | `{ "action": "heartbeat", "leaseId": "UUID" }` | `{ "ok": true }` |
| POST | `/v1/control` | `{ "action": "release", "leaseId": "UUID" }` | `{ "ok": true }` |
| POST | `/v1/actions` | `{ "leaseId": "UUID", "action": { ... } }` | Started job. |
| POST | `/v1/cancel` | `{ "leaseId": "UUID" }` | `{ "ok": true }` |
| POST | `/v1/stop` | `{}` | `{ "ok": true }` |

Create a fresh canonical UUID for each control session. Acquire is exclusive, and heartbeat/release/action/cancel require the current owner. Stop requires the bridge bearer token but no lease, allowing a second process to stop the owner. An expired or released UUID cannot renew control. After manual takeover, only a new explicit acquire starts another session.

Heartbeat every two seconds. After eight seconds without a heartbeat, movement, digging, and item use are cancelled. Fabric checks the monotonic lease clock each client tick; Node uses a 250 ms watchdog. A paused/frozen game cannot execute ticks; lease expiry is enforced when its event loop resumes. Minecraft requests are dispatched on the client thread, with queued requests discarded if they time out before execution.

Actions:

```json
{ "type": "goto", "x": 10, "y": 64, "z": -20 }
{ "type": "set_home" }
{ "type": "home" }
{ "type": "collect", "block": "minecraft:oak_log", "count": 8 }
{ "type": "eat" }
{ "type": "deposit", "item": "minecraft:oak_log", "count": 8 }
{ "type": "inspect_storage" }
{ "type": "inspect_storage", "containers": [{ "x": 3, "y": 64, "z": -2 }] }
{ "type": "withdraw", "item": "minecraft:oak_log", "count": 8 }
{ "type": "craft", "item": "minecraft:stone_pickaxe", "count": 1 }
{ "type": "wait", "seconds": 30 }
```

Coordinates must be finite, X/Z within ±29,999,984 and Y within -64..320. Collection count must be an integer in 1..64. Deposit count is optional (all held items when omitted) and must be an integer in 1..2304. Wait duration is 1..3600 seconds. `inspect_storage` `containers`, when present, lists 1..16 integer block positions within the same world bounds. Collection targets are listed in the [usage guide](USAGE.md#collection-and-survival). Most actions have a 180-second timeout; wait's timeout is its duration plus five seconds. Survival retreat has a separate 60-second limit. Collection is measured by inventory increase, not blocks broken. Real backends require a pickaxe for cobblestone collection and fail if no usable pickaxe remains while mining. Deposit stores the item in the nearest chest, trapped chest, or barrel within 16 blocks. It fails without moving when too few items are held, and fails with the stored count when the container fills. Fabric also supports deposits and storage inspection; only the container opened by the active action is exempt from screen-triggered takeover.

Withdraw takes an item from one chest, trapped chest, or barrel within 16 blocks. It chooses the nearest container whose last-observed contents include the item, then the nearest container not yet opened this session, and reports which container it used. Withdraw count is optional (every matching item in that container when omitted) and must be an integer in 1..2304. It fails without moving when no candidate exists. It fails with `withdrew N of M` when the container holds fewer than requested, and with `Inventory full; withdrew N of M <item>.` when no main inventory slot or matching stack has room; items already moved stay in the inventory. Like deposit, the job carries `container` with the contents read immediately before the transfer, and the container's observation is updated with the contents read during the action.

Craft makes at least `count` (1..64) of one allowlisted output by repeating whole vanilla 1.21.1 recipes: `<wood>_planks` for the eight overworld wood types listed for collection, `stick`, `crafting_table`, and `torch` in the player's 2×2 grid; `chest`, `furnace`, and wooden and stone `pickaxe`, `axe`, and `shovel` at a crafting table. `src/recipes.js` lists the allowlist, yields, and accepted ingredients. Craft checks ingredients before moving and fails with the missing amounts, for example `Missing ingredients for 1 stone_pickaxe: 1 more of cobblestone/blackstone/cobbled_deepslate.` A table recipe uses the nearest crafting table within 16 blocks, walking into reach without digging. When none is within 16 blocks and a crafting table is held, craft first places it on a free block next to the player and reports its coordinates; otherwise it fails before moving. Cancellation, takeover, expiry, and stop are checked between crafts; completed crafts stay in the inventory, and an inventory with no room for the output fails with `Inventory full; crafted N of M <item>.` The job message reports how many items were crafted. Only the crafting table screen opened by the active craft is exempt from screen-triggered takeover on Fabric.

Jobs contain `id`, `type`, `status`, and `message`. A deposit job that opened its container also carries `container`: `name`, `x`, `y`, `z` (the canonical position, the lower half of a double chest) and `before`, that container's contents read in the same window immediately before the transfer. It is present on failed and cancelled deposits too, because items may have moved before the failure. Fabric reads `before` from the first contents packet the opened screen receives, before any click; it adds `container` when the job ends, so a running deposit job does not carry it. Status is `running`, `completed`, `failed`, or `cancelled`. Poll state to track the current job; at most one action runs at a time. The last terminal job remains observable until a new action starts. A terminal status means the action stopped, not that the agent's broader goal succeeded.

The CLI planner's explicit inventory/home criteria are checked separately by the client; they are not bridge endpoints. See [Ollama task verification](USAGE.md#run-an-ollama-task) for their scope and exit statuses.

Real-backend collection completes only when its item quota is met and the player is back near the starting point. An unreachable return trip is `failed` even if the inventory quota was met. When matching blocks run out before the quota is met, collection attempts the return trip and remains `failed`; the message reports the inventory total/target and return outcome. When no main inventory slot (hotbar and inventory, not armour or offhand) is empty and no stack of the drop has room, collection stops promptly on every backend with a message containing `Inventory full; collected N of M <block>.`, keeps its progress, and makes the same bounded return attempt. Always observe fresh inventory before retrying a partial collection. Cancellation, lease expiry, death, or a survival interruption does not start a collection return trip. Both real backends allow up to 180 seconds of mining plus up to 60 additional seconds to return, including after a mining deadline. The bot harness reserves that recovery budget separately from mining; session cancellation still stops both phases.

State includes `protocol`, `backend`, `connected`, `paused`, `mode` (`manual` or `agent`), `job`, and, when connected, `player`, `inventory`, `home`, `threats`, `blocks`, and `survival`. All current backends expose `containers`: nearby and previously opened containers with `name`, `x`, `y`, `z`, and `items` (`null` until opened, then the last contents seen). Opened containers also carry `firstSeen`, their contents when this session first opened them, and `observedAt`, the Unix-millisecond time of the latest read. Fabric and the bot also report `members` (coordinates sharing the inventory now) and `sources` (stable baseline IDs with their first-observed `items`). Merges combine baseline sources; splits preserve that history on the resulting inventories. Verification counts current inventories by canonical coordinate and subtracts each baseline source once, including sources first discovered during the task. Historical baseline IDs do not identify which containers share an inventory now. `inspect_storage` without `containers` reopens every previously opened container for the current identity, requires each to be within 16 blocks when approached, and returns near the inspection start without digging. With `containers`, it reopens only the listed positions instead; a position may name either half of a double chest, and each inventory is read once. A listed position that this session has not opened, or that holds no chest or barrel, fails the action before anything moves, and only the listed containers must be within 16 blocks. It fails if inspection or return fails, rather than silently using old contents. It has the ordinary action deadline and cancellation semantics. On every bundled backend, the planner verifies deposits against the containers its own deposits reported, each baselined by its `before` contents at the task's first deposit into it, and reopens only those (plus inventories descended from them through chest merges or splits) before the final check. For a backend that does not report deposit containers, it inspects every known container before the baseline and the final deposit check. Ordinary observations and intermediate progress are still cached snapshots. Reads across containers are sequential, not atomic. Fabric also exposes `recovering` and `focusPaused`. `focusPaused` is true when the only blocker is the pause menu Minecraft opened because its window lost focus (for example, switching to a terminal to run the CLI); acquire closes that menu and disables pause-on-focus-loss for the session. Other screens, such as inventories, chat, or a menu the player opened while focused, still block takeover. Nearby blocks and threats are partial loaded-world observations. Fabric and Mineflayer threats include `type`, `distance`, and entity coordinates `x`, `y`, `z` for spatial reports. Older backends may omit coordinates; those entries remain counted as unlocated. Different backends can expose additional fields.

Bridges also expose `stopping`. Fabric uses it while a cancelled container opening awaits its ordered server acknowledgement; a late screen reply is closed without clicks. Player block or entity interaction during storage releases control, and a new interaction is held while that earlier opening is unresolved. Cancellation stops inputs immediately, but an inventory or pathfinder operation can still be awaiting a reply. While it settles, the bridge rejects new actions and takeover instead of overlapping operations. A world, player, or dimension change releases control even when no action is running.

Player data includes name, UUID, health, hunger, dimension, and position. Inventory entries include slot, namespaced item name, and count. Item slots follow the underlying backend's inventory model and are observational; clients should identify items by name rather than assume the same slot numbers in both backends.
